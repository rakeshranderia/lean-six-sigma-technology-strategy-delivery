# 1. Framework Overview

## Purpose

Technology management already contains many mature disciplines: strategy, enterprise architecture, portfolio management, program management, project management, Agile delivery, service management, cybersecurity, data governance and operational improvement.

Lean Six Sigma should not be positioned as a replacement for any of them.

Its value is different.

It provides a repeatable way to connect:

**Problem → Evidence → Cause → Improvement → Sustained Outcome**

That pattern is useful whether the intervention eventually becomes:

- a strategic roadmap;
- an architecture change;
- a portfolio reprioritisation;
- a transformation program;
- a project;
- an automation initiative;
- a service improvement;
- a technology-estate rationalisation;
- a data-quality initiative;
- or a new operating model.

The significant overlap with technology planning and delivery exists because both disciplines are ultimately concerned with **controlled change against an intended outcome**.

---

## Why the overlap matters

Technology roadmaps can easily become collections of desired projects.

Portfolio governance can become a funding and status process.

Programs can become containers for related projects.

Projects can become focused on scope, schedule and budget.

Operations can become focused on service continuity.

Every one of those activities is necessary. None, by itself, proves that the original business problem improved.

Lean Six Sigma contributes a persistent evidence chain:

1. **Define** what needs to improve.
2. **Measure** the current state.
3. **Analyse** what is causing the current state.
4. **Improve** through an intervention or target state.
5. **Control** the improved state and prove that it is sustained.

This makes DMAIC useful from the boardroom to the service desk.

---

## The technology management lifecycle

The framework uses the following lifecycle:

**Business Need → Strategy → Roadmap → Portfolio → Program → Project → Operations → Benefits**

Each level has a different decision purpose.

### Business Need
A problem, opportunity, constraint, customer outcome, regulatory obligation or capability requirement exists.

### Strategy
Technology direction is shaped around business outcomes, constraints, principles and target capabilities.

### Roadmap
The gap between current and target state is sequenced into a practical change path.

### Portfolio
Competing initiatives are assessed against strategic fit, value, risk, capacity, dependency and affordability.

### Program
Related changes are coordinated to deliver an outcome that individual projects cannot achieve alone.

### Project
A defined change is delivered within agreed scope, governance and constraints.

### Operations
The changed capability is supported, monitored, secured and improved.

### Benefits
Actual outcomes are compared with the original baseline and investment rationale.

The result feeds the next planning cycle.

---

## DMAIC across the lifecycle

DMAIC is not confined to one level.

### Define can occur at strategy level
A board or executive team may define a capability problem such as:

> Our technology estate is too fragmented and expensive to support our growth model.

### Measure can occur at portfolio level
The organisation can establish:

- application count;
- vendor count;
- annual run cost;
- licence utilisation;
- support effort;
- incident volume;
- integration count;
- technical debt;
- risk exposure.

### Analyse can occur at program level
A transformation team may identify:

- duplication;
- historic acquisitions;
- inconsistent standards;
- ownership gaps;
- custom integrations;
- poor lifecycle management;
- obsolete platforms.

### Improve can occur through multiple projects
The response might include:

- consolidation;
- migration;
- architecture standards;
- contract changes;
- decommissioning;
- process redesign;
- data integration;
- automation.

### Control occurs in operations and governance
The new state is sustained through:

- service ownership;
- architecture governance;
- procurement standards;
- lifecycle reviews;
- cost and utilisation metrics;
- portfolio gates;
- benefits tracking.

The power of the model is that the same problem can be traced across all of those layers.

---

## What Lean adds

Lean adds another dimension: flow and waste.

In technology environments, waste can appear as:

- approval queues;
- manual re-entry;
- duplicated systems;
- unused licences;
- repeated hand-offs;
- avoidable incidents;
- rework;
- over-engineering;
- excessive customisation;
- redundant reporting;
- platform proliferation;
- unresolved technical debt.

These are not always “defects” in a traditional manufacturing sense, but they consume capacity and reduce value.

Phase 2 will expand the Lean translation in detail.

---

## What Six Sigma adds

Six Sigma adds disciplined attention to:

- variation;
- baseline performance;
- data quality;
- root cause;
- measurable outcomes;
- control;
- sustainability.

In technology, that can mean asking whether:

- incident performance is stable;
- project outcomes are repeatable;
- release quality is improving;
- service targets are consistently met;
- customer onboarding time is reducing;
- automation is actually removing effort;
- application rationalisation is lowering cost;
- AI adoption is creating measurable value;
- security controls are reducing exposure.

The goal is not to force statistical analysis where it adds little value. The goal is to make evidence stronger than assumption.

---

## What this framework is not

This framework is not:

- a replacement for PRINCE2, PMBOK or Agile;
- a formal Six Sigma certification curriculum;
- a requirement to use control charts for every project;
- a claim that every technology problem is a process problem;
- a rigid sequence that prevents iterative delivery;
- a governance layer that exists for its own sake.

It is a way to strengthen the reasoning that connects technology investment to business improvement.

---

## Core principle

The framework can be summarised in one line:

> **Technology delivery should be able to explain what problem it is improving, what evidence established the problem, why the chosen intervention addresses the cause, and how the organisation will know the improvement lasted.**
